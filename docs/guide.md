# Ötzi User Guide

## What is Ötzi?

Ötzi is a self-hosted threshold Bitcoin vault. A group of N parties creates one Taproot address together; any T of them can spend from it, fewer cannot. Each party holds a password-encrypted share file. The server coordinates, builds transactions and broadcasts them, but never holds key material.

Typical setups: a 2-of-3 between partners, a 3-of-5 treasury, a 2-of-2 between a person and a backup device kept by someone else.

## Vault Architecture

The vault key is generated by FROST distributed key generation (RFC 9591, secp256k1-SHA256-TR). The result is:

- **One Taproot address** (`bc1p…` on mainnet, `tb1p…` on testnet4/signet). It is a key-path-only address: on chain it looks like any single-signature Taproot wallet.
- **One share file per party**, encrypted in the browser with a password the party chooses.
- **The vault's public key package** on the server, from which the address, threshold and party count are derived.

Spending produces ordinary BIP340 Schnorr signatures. Any T share files, with their passwords, can sign.

## Setup Flow

### 1. Network

Choose `mainnet`, `testnet4` or `signet`. Try the full flow on testnet4 or signet first.

Already have a backup? Use **Restore from Backup** on this step.

### 2. Sign-in

- **Admin password** (default) — one password protects settings and starting sends. Co-signers never need to sign in: they join ceremonies with a session code and their share file.
- **Accounts** — named users with roles. Each user signs in with a **passkey** (Face ID, Touch ID, Windows Hello, a phone or a security key) or with a **Bitcoin wallet** that can sign messages. The admin invites new users with invite codes. Accounts mode keeps its configuration in persistent storage.

Passkeys need the instance to be served over HTTPS on its own domain (or `localhost`).

### 3. Storage Mode

With admin-password sign-in, choose how the server keeps its configuration: persistent, encrypted persistent, or encrypted portable. See [portable-mode.md](portable-mode.md).

### 4. DKG Ceremony

1. One party chooses the **threshold** (T) and **number of parties** (N) and clicks **Create Session**.
2. Share the session link (or 6-character code) with the other N−1 parties.
3. Once everyone has joined, compare the **session fingerprint** with each other (read it out on a call, for example) and click **Fingerprint matches**. Nothing secret is sent before you confirm.
4. The ceremony runs: **Commit**, **Shares**, **Verify**. Do not refresh the page while it runs.
5. On **Complete** — reached only once every party has verified the new key — everyone sees the vault address. Compare it with each other.
6. Each party clicks **Download Share File**, chooses a password, and stores the file safely.

If any party misbehaves or a message is corrupted, the ceremony stops with an error naming the party at fault.

An admin who has a share file of an existing vault can instead choose **Use existing share file** to connect this instance to that vault.

## Sending Bitcoin

### Initiator

1. Click **Send** on the vault page.
2. Enter or pick the **recipient** from the address book.
3. Enter the **amount** (BTC, mBTC, µBTC or sats), or click **Max** to send everything.
4. Pick a **fee rate** (Low / Normal / High from current estimates, or Custom).
5. Click **Review**. Check recipient, amount, fee and change, then **Approve & sign**.
6. Load your **share file** and password. A signing session opens.
7. Send the session link to T−1 co-signers and compare the session fingerprint with them.

### Co-signer

1. Open the session link (or click **Join** and enter the code).
2. Load your share file and password.
3. Review what the transaction pays: each recipient (with its address book label), the change returning to the vault, and the fee. Compare the session fingerprint with the initiator.
4. Click **Approve & sign**, or **Reject** to stop the session.

Your browser computes the transaction's signature hashes itself from the transaction you reviewed.

### Result

After T approvals, the initiator's browser combines the signatures and the server broadcasts the transaction. Everyone sees the transaction ID. Transactions signal replace-by-fee (BIP125).

Only confirmed coins are spent. Incoming payments show as pending until they confirm.

## Address Book

**Settings > Address Book** lists named addresses for the instance's network.

- **Add**, **edit** and **remove** entries (admin).
- **Export** saves the book as `otzi-address-book-<network>.otzi.json`.
- **Import** reads an `.otzi.json` address book and shows what it would change. Choose:
  - **Merge** — add new addresses and update labels of existing ones; keep everything else.
  - **Replace** — the file's entries become the whole book.

The file format is described by [`otzi-address-book-schema.json`](otzi-address-book-schema.json):

```json
{
  "kind": "otzi-address-book",
  "version": 1,
  "network": "mainnet",
  "entries": [
    { "label": "Cold storage", "address": "bc1p5d7rjq7g6rdk2yhzks9smlaqtedr4dekq08ge8ztwac72sfr9rusxg3297" },
    { "label": "Exchange deposit", "address": "bc1qar0srrr7xfkvy5l643lydnw9re59gtzzwf5mdq", "note": "Rotates monthly" }
  ]
}
```

## Accounts

In accounts mode:

### Roles

| Role | Can view | Can start sends | Can edit settings |
|------|---------|-----------------|-------------------|
| **Admin** | Everything | Yes | Yes |
| **User** | Everything | Yes | No |
| **Everybody** | Configurable | No | No |

Co-signing never requires an account: a session link and a share file are enough.

### Signing in

- **Passkey** — click **Sign in with passkey** and confirm on your device.
- **Bitcoin wallet** — a detected browser wallet (Unisat, OKX) signs the challenge directly with **Sign in with Unisat** / **Sign in with OKX Wallet**. Any other wallet works too: choose **Sign in with any Bitcoin wallet**, copy the shown message, sign it in your wallet (Sparrow, Electrum, Bitcoin Core, a hardware wallet), and paste the address and signature. BIP-322 and legacy signmessage signatures are accepted.

### Adding users

- **Invite codes** — the admin creates a code with a role, maximum uses and expiry. The new user enters it and registers a passkey or a Bitcoin wallet.
- **Bitcoin address** — the admin can add a user directly by Bitcoin address; that user then signs in with that wallet.

The last admin cannot be removed or demoted.

### Session tokens

Sign-ins last 6 hours. The admin chooses whether visitors who are not signed in can view the vault page.

## Settings

- **Instance** — network, vault address, threshold, and the **chain API** (Esplora URL). Leave the chain API empty to use mempool.space, or point it at your own mempool/electrs server so your vault address is not revealed to a third party.
- **Address Book** — see above.
- **Users** — accounts mode only.
- **Hosting** — domain, port, path and HTTPS. Used for session links and, in Docker, for Caddy with automatic Let's Encrypt certificates.
- **Backup** — download an encrypted backup of the configuration and users; restore one.
- **Reset** — wipe the instance. Share files are unaffected and still control the vault.

## Security Model

- **Threshold FROST** — BIP340 Schnorr signatures via FROST (RFC 9591). No party ever holds the full private key.
- **Approve what you sign** — every co-signer decodes the unsigned transaction and computes signature hashes locally. Lying about spent coins only produces signatures the network rejects.
- **Verified DKG** — the ceremony ends with all parties signing under the new key, proving everyone holds a consistent share.
- **Share encryption** — AES-256-GCM with a PBKDF2-derived key (600k iterations). Passwords never leave the browser.
- **E2E relay** — ECDH key agreement + AES-256-GCM. The relay forwards ciphertext only.
- **Server verification** — every signature is checked before broadcast; each transaction is broadcast once.
- **No secrets on the server** — only public key data, the address book, settings and users.
